## 新增需求

### 需求：定位并验证 Windows BSP 碰撞数据

系统必须在 Windows x86 L4D2 进程中定位当前地图已加载的 BSP 碰撞数据。除非所有必需指针、数量、偏移和结构假设均通过验证，否则系统必须拒绝启用该功能。

#### 场景：存在有效的 BSP 碰撞数据

- **当** 本地服务器地图完成加载
- **那么** 系统必须定位 `g_BSPData`
- **并且** 验证必需的 node、leaf、leafbrush、brush、brush-side 和 box-brush 数组
- **并且** 将当前地图代际的 BSP 碰撞查询标记为就绪

#### 场景：无法证明 BSP 碰撞数据有效

- **当** 地址定位或结构验证失败
- **那么** 系统不得执行任何 BSP 内存写入
- **并且** 必须保留现有传送门穿越行为
- **并且** 必须记录足够诊断问题的验证失败信息

### 需求：传送门放置时解析承载 brush

系统必须复用成功放置传送门时的表面数据，解析承载每扇传送门的 BSP 世界 brush。

#### 场景：传送门放置在受支持的世界 brush 上

- **当** 传送门在世界几何体上的放置成功
- **那么** 系统必须使用放置命中位置和表面法线定位对应的 BSP leaf 和 brush
- **并且** 保存 brush 索引、原始 contents、传送门所有者和地图代际

#### 场景：未找到有效承载 brush

- **当** 所有向表面内部偏移的采样点都无法识别有效的 `MASK_PLAYERSOLID` brush
- **那么** 系统必须保持 BSP 碰撞不变
- **并且** 将该传送门绑定标记为未解析
- **并且** 使用现有穿越兜底方案

### 需求：brush 碰撞修改必须可恢复且具备事务性

系统必须把所有唯一传送门 brush 的修改作为一个可恢复事务处理。

#### 场景：两扇传送门使用不同 brush

- **当** 蓝门和橙门绑定都有效并启用成对挖空
- **那么** 系统必须只保存一次每个 brush 的原始 contents
- **并且** 把两个 brush 的 contents 都设置为 `CONTENTS_EMPTY`

#### 场景：两扇传送门共用一个 brush

- **当** 蓝门和橙门解析到相同 brush 索引
- **那么** 系统只能写入该 brush 一次
- **并且** 必须同时保留两扇门的所有权
- **并且** 只有两个所有者都释放后才能恢复该 brush

#### 场景：成对激活部分失败

- **当** 某个目标验证或写入失败，而另一个目标已经被修改
- **那么** 系统必须立即回滚本次激活已经完成的所有写入
- **并且** 报告激活失败

#### 场景：重复请求恢复

- **当** 恢复操作被调用多次
- **那么** 后续调用必须是安全的空操作
- **并且** 不得覆盖无关的内存值

### 需求：阶段一提供无约束的整块 brush 挖空

阶段一必须移除承载 brush 的完整碰撞，不增加玩家附近检测，也不创建 blocker 实体，以便测试最原始的行为。

#### 场景：两扇传送门都有效且绑定成功

- **当** 阶段一挖空功能已启用
- **那么** 系统必须忽略玩家距离并启用成对挖空
- **并且** 在传送门组合持续有效期间保持挖空

#### 场景：禁用旧绕过后玩家使用传送门

- **当** 成对挖空已激活，并且本地玩家穿过入口孔径
- **那么** 原始客户端和本地服务端移动 trace 必须允许玩家穿过承载墙体
- **并且** 现有穿越状态机必须把玩家传送到关联出口

#### 场景：测试无约束副作用

- **当** 阶段一挖空已激活
- **那么** 系统必须允许测试者观察整块 brush 被移除的全部后果
- **并且** 不得暗中增加附近检测或 blocker 约束

### 需求：所有破坏性生命周期变化都必须恢复碰撞

系统必须在丢弃仍有效的地图地址或传送门所有权之前恢复已修改 brush 的 contents。

#### 场景：重新放置传送门

- **当** 活跃传送门成功重新绑定到另一个 brush
- **那么** 必须释放旧 brush 上该传送门的所有权
- **并且** 没有剩余所有者的 brush 必须恢复
- **并且** 新的有效传送门组合必须以事务方式激活

#### 场景：传送门关闭或失效

- **当** 任一传送门无法再组成有效传送门对
- **那么** 系统必须恢复全部成对挖空

#### 场景：地图或 DLL 关闭

- **当** 开始关卡关闭、传送门系统关闭或 DLL 卸载
- **那么** 系统必须在 BSP 地图代际失效前调用同一个幂等恢复路径

### 需求：现有传送门穿越基础设施保持权威

BSP 碰撞系统只能控制承载 brush 的碰撞，不得重复实现跨越检测、坐标变换、传送、预测或视觉职责。

#### 场景：玩家穿过已打开的承载 brush

- **当** 现有状态机检测到玩家跨越传送门平面
- **那么** `PortalTransform` 必须计算变换后的位置、速度和角度
- **并且** `PortalPlayerTeleport` 必须执行本地服务端传送
- **并且** 现有过渡和渲染系统必须继续正常运行

#### 场景：BSP 挖空不可用

- **当** BSP 初始化或传送门 brush 绑定失败
- **那么** 现有碰撞桥和受控穿越路径必须继续作为兜底方案

### 需求：诊断模式必须证明因果关系和恢复行为

系统必须提供诊断控制和日志，能够区分 BSP 修改效果与现有碰撞绕过效果。

#### 场景：选择 BSP 因果测试

- **当** 启用 BSP 挖空，同时为了测试禁用旧 trace 清除/noclip 绕过
- **那么** 日志必须明确标识当前模式
- **并且** 玩家成功穿越必须能够归因于 BSP 挖空

#### 场景：brush 被修改并恢复

- **当** 一次修改生命周期完成
- **那么** 日志必须记录地图代际、传送门所有者、brush 索引、原始 contents、替换 contents、当前 contents 和操作原因
- **并且** 诊断 trace 必须展示修改前、修改后和恢复后的碰撞结果

### 需求：阶段二把挖空限制在本地玩家的穿越附近

阶段一验收后，阶段二必须能够选择性使用带迟滞的可配置传送门局部空间附近策略来启用挖空。

#### 场景：玩家进入传送门激活范围

- **当** 本地玩家锚点进入任一活跃传送门扩展后的局部宽度、高度和进入深度范围
- **那么** 必须启用成对挖空

#### 场景：玩家在阈值边缘移动

- **当** 挖空已经激活，玩家离开进入阈值但仍处于更大的离开阈值内
- **那么** 必须保持挖空，不能反复开关

#### 场景：穿越仍在进行

- **当** 穿越阶段为 `ApproachingPortal`、`IntersectingPortal`、`CommittingTeleport` 或 `ExitingPortal`
- **那么** 即使某一帧附近检测为假，也必须保持挖空

#### 场景：玩家安全离开传送门附近

- **当** 玩家已离开两扇门的离开范围，并且穿越不再活跃
- **那么** 系统必须恢复原始 brush 碰撞

### 需求：阶段三可以使用服务端 blocker 约束开口区域

阶段二的证据表明确有空间约束需要后，阶段三可以在传送门孔径周围创建本地服务端 blocker；但必须先验证目标 L4D2 版本中的实际行为。

#### 场景：blocker 能力尚未验证

- **当** 旋转边界、碰撞行为或生命周期清理尚未得到证明
- **那么** 系统不得默认启用 blocker 约束

#### 场景：启用 blocker 约束

- **当** 已验证的 blocker 几何体在挖空 brush 周围创建成功
- **那么** 本地玩家必须仍能穿过传送门孔径
- **并且** 周围经过测试的墙体区域必须保持阻挡
- **并且** 任意部分创建失败都必须删除已创建的 blocker 并恢复 brush

## 范围约束

- 本能力仅面向单人游戏/本地服务器。
- 验收只关注本地幸存者玩家的移动和传送门传送。
- 本能力不声明支持 NPC、普通感染者、特殊感染者、AI 导航、子弹、近战 trace、投掷物、物理道具或远程服务器。

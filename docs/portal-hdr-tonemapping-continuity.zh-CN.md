# L4D2 传送门 HDR / Tonemapping 视觉连续性问题总结

## 背景

当前传送门穿越逻辑在几何连续性上已经基本成立：相机朝向、传送门配对、Render Target 视角、穿越后的坐标变换都没有明显错误。

但在真正支持穿越之后，出现了一个新的视觉问题：

- 穿越前一帧和穿越后一帧之间，画面亮度、雾感、天空曝光会明显跳变。
- 场景方位和视角没有明显突变，所以问题看起来更像是环境光照或雾气状态突然变了。
- 如果玩家贴近传送门等待 2-3 秒，门后画面会逐渐从过曝恢复到正常，再穿越时突兀感明显降低。
- 如果玩家直接走过传送门，视觉突变仍然明显。

这个现象最开始容易被误判为 fog、skybox、leaf、area 或光照环境状态没有同步，但最终确认根因是 Source 引擎 HDR dynamic tonemapping，也就是动态曝光 / 眼睛适应。

## 排查过程

### 1. 先排除了环境状态不一致

为了确认是不是环境状态问题，曾在穿越逻辑和传送门渲染逻辑中加入诊断日志：

- `[PortalEnvironment]`：记录玩家当前位置、传送目标位置附近的 leaf、area、fog、skybox、tonemap controller、ambient light、point contents 等状态。
- `[PortalRenderState]`：记录传送门 Render Target 渲染过程中的 tone scale 等渲染状态。
- 后续因为渲染 hook 调用频率极高，日志需要节流，否则一次穿越就会产生大量日志。

日志结论是：fog、skybox、leaf、area 等状态没有表现出足以解释画面突变的异常。

也就是说，问题并不是“穿越后进入了错误的雾区 / 错误的 skybox / 错误的区域光照”。

### 2. Render-time tone scale 与现象高度吻合

真正关键的线索来自 `[PortalRenderState]`：

- 直接穿越时，传送门渲染相关的 tone scale 曾处在较高值，大约 `1.6x`。
- 贴近传送门等待后再穿越时，tone scale 会逐渐下降并稳定到较低值，大约 `1.2x`。
- 用户观察到的现象也完全一致：贴近门等待时，过亮的天空 / 门后画面会慢慢恢复正常，随后穿越就顺畅很多。

这说明问题更像是一个随时间收敛的曝光适应过程，而不是静态的光照、雾气或相机变换错误。

### 3. 手动 tone clamp 尝试没有命中正确时机

之前尝试过在穿越 / visual transition 时机读取并设置 tone scale，但日志显示这些时机经常读到的是 `1.000`。

而真正导致视觉差异的 tone scale 出现在更后面的传送门渲染过程中。

这说明手动 clamp 的位置不对：问题不在穿越变换本身，而在 Source 渲染管线后续的 HDR 动态曝光路径里。

## 根因

根因是 Source 引擎的 HDR dynamic tonemapping / eye adaptation。

传送门渲染会制造一个特殊场景：

- 穿越前，目标地点画面只显示在传送门 Render Target 里，占据屏幕的一部分。
- 玩家越靠近传送门，门后画面占屏幕比例越大，HDR 动态曝光会逐渐向门后画面的亮度适应。
- 如果玩家贴近门等待，曝光有时间收敛，所以穿越时画面变化较小。
- 如果玩家直接穿越，主视角突然变成目标地点画面，但 HDR 曝光还没有完成适应，于是相邻两帧出现明显亮度跳变。

因此，这不是传送门几何变换问题，也不是 fog / skybox 环境状态没有同步，而是后处理曝光状态在时间上的不连续。

它看起来像雾气或光照突变，是因为 HDR 曝光会影响整张画面：天空、远景雾感、墙面亮度、地面灰度都会一起变化。

## 已确认方案

官方控制台变量 `mat_dynamic_tonemapping` 可以关闭 dynamic tonemapping。

传送门状态下的实际方案是：

1. 当玩家处于传送门相关状态时，关闭 dynamic tonemapping。
2. 当玩家离开传送门状态后，恢复之前的 cvar 值。

控制台验证命令：

```text
mat_dynamic_tonemapping 0
```

恢复命令：

```text
mat_dynamic_tonemapping 1
```

实测结果：在传送门状态下关闭该功能后，直接穿越时的曝光突变可以被消除或显著降低，并且整体视觉副作用很小，可以接受。

## 相关诊断变量

`mat_hdr_manual_tonemap_rate` 会影响 HDR 曝光适应速度：

```text
mat_hdr_manual_tonemap_rate 0.25
```

这个变量对诊断很有帮助，因为它会改变门后画面从过曝逐渐恢复正常的速度。

但它不适合作为最终修复方案，因为它只是改变“适应速度”，不能从根本上消除“直接穿越”和“等待后穿越”之间的曝光状态差异。

最终更合适的控制点是 `mat_dynamic_tonemapping`：在传送门状态下直接关闭动态曝光，避免时间适应造成的跨帧不连续。

## 实现建议

建议实现一个很小的 portal tonemapping guard，而不是永久全局关闭该 cvar。

推荐行为：

- 进入传送门状态时，查找 `mat_dynamic_tonemapping`，保存原始值，然后设置为 `0`。
- 以下状态期间保持关闭：
  - 玩家正在执行穿越逻辑。
  - 玩家非常接近传送门平面，或者正在与传送门平面相交。
  - 穿越后的短暂视觉连续性冷却期仍然有效。
- 离开传送门状态后，恢复之前保存的值。
- 地图切换、DLL 卸载、portal system shutdown 时必须兜底恢复。
- 只在状态切换时写 cvar，不要每帧写。
- 日志只记录状态变化，不要在 render hook 中高频打印。

建议日志格式：

```text
[PortalTone] dynamic tonemapping disabled previous=1 reason=near-portal
[PortalTone] dynamic tonemapping restored value=1 reason=portal-state-exit
```

之前的排查已经证明，传送门渲染 hook 调用频率非常高，如果在里面逐帧打印日志，一次穿越就会让日志暴涨。

## 测试清单

后续实现或重构时，可以按这个清单验证：

- 直接走过传送门时，不再出现明显曝光跳变。
- 贴近传送门等待 2-3 秒后再穿越，画面仍然顺畅。
- 穿越后画面不会明显偏暗。
- 离开传送门状态后，普通游戏画面会恢复原始 `mat_dynamic_tonemapping` 设置。
- 地图切换、退出、重新注入时，不会把该 cvar 意外保持在关闭状态。
- 日志只出现状态切换记录，不出现逐帧刷屏。

## 经验沉淀

- 看起来像 fog / lighting 的问题，不一定来自环境状态，也可能来自 HDR 后处理曝光。
- “贴近传送门等待后问题减轻”是典型的时间适应信号。
- 传送门视觉连续性不只取决于相机变换和目标点环境状态，还取决于渲染管线中的后处理状态。
- 对 Source 引擎这类内部渲染状态，使用官方 cvar 控制有时比在穿越时机手动改 tone scale 更可靠，因为真正的曝光值可能在后续 render pass 才更新。

# L4D2 注入式视觉奇观插件头脑风暴

**日期:** 2026-06-12  
**阶段:** 创意收敛，尚未进入详细设计或实现  
**目标:** 利用工程已经具备的 Portal 渲染、视图修改、模型渲染和实体访问能力，探索适合公开展示技术实力的视觉奇观插件。

## 1. 背景

当前工程虽然以复刻 Portal 为主，但已经具备一组可以独立复用的渲染能力：

- 在 `BaseClient::RenderView` 中读取和修改主视角 `CViewSetup`。
- 将另一个视角渲染到自定义 RenderTarget。
- 使用 Stencil 将另一个场景限制在指定模型或屏幕区域内。
- 使用 Clip Plane 裁掉错误方向的世界几何。
- 在 `DrawModelExecute` 中识别模型、覆盖材质并参与递归渲染。
- 通过状态机管理跨帧动画和视觉过渡。
- 通过 `CreateMove`、实体列表和 EngineTrace 获取玩家、实体与空间信息。
- 在需要时创建、移动和复用 `prop_dynamic` 等实体。

因此，项目可以从“传送门功能”扩展成一个“局部空间重写与多视图合成实验平台”。本轮讨论聚焦视觉奇观，不优先考虑战斗增强或多人竞技优势。

## 2. 创意方向

### 2.1 随机门网络

地图中的普通门不再只是相邻房间的入口，而是随机连接到地图中的另一扇门，甚至另一张地图的预设场景。

#### 核心演出

1. 玩家接近一扇门时，门缝或门框内逐渐出现目标地点的实时画面。
2. 门关闭时连接尚未确定；第一次开门时随机选择目的地并锁定连接。
3. 门打开后，门框内显示目标空间，玩家可以直接穿越。
4. 门再次关闭后，可以保持连接，也可以重新随机。

#### 技术层次

- **视觉原型:** 只选择一对预设门，在门框中渲染另一个固定摄像机视角。
- **单地图穿越:** 自动建立本地图中两扇门的视觉与 teleport 连接。
- **随机门图:** 多扇门形成动态有向图，需要避免死循环、无出口和任务流程破坏。
- **跨地图版本:** 需要处理地图加载、实体状态恢复和场景伪连续，复杂度远高于单地图版本。

#### 展示价值

很高。玩家熟悉的 L4D2 地图会被重组为不可预测的空间迷宫，而且 Portal 技术不再依赖 Portal 模型，具有明确的“空间重写”辨识度。

### 2.2 世界折叠

参考《盗梦空间》的城市折叠演出：远方建筑、街道或天空逐渐向玩家头顶翻转，最终形成闭合或交叠的空间。

#### 核心演出

1. 镜头前方的世界保持正常。
2. 远处世界从某条折线开始抬升。
3. 上方出现另一个旋转后的地图视图，与当前地面逐渐接近。
4. 折叠完成后停留数秒，再逆向恢复。

#### 可行实现

- **镜头版 MVP:** 动画修改视角 roll、pitch 和 FOV，营造世界倾覆感，但不会真正形成两块不同朝向的世界。
- **多视图版:** 将同一世界以不同旋转视角渲染多次，通过屏幕区域或 Stencil 分割后合成。
- **几何版:** 识别并转换地图几何或创建替代模型，效果最真实，但不适合作为第一阶段。

#### 展示价值

极高。真正的多视图折叠能直接展示视图变换、裁剪、合成和跨帧动画能力。

### 2.3 无限建筑

窗户、镜子、电视、画框或自定义门框内部递归出现当前房间，形成空间套空间的无限回廊。

#### 核心演出

1. 玩家看向一个普通框状表面。
2. 表面内部显示当前房间的另一个缩放或旋转版本。
3. 内层房间中仍然存在同一个框，因此继续递归。
4. 每层可加入轻微旋转、缩放、色调或时间差，避免只是普通镜子。

#### 可行实现

- 复用现有 `RenderPortalViewRecursive()`、RenderTarget 池、Stencil 和 Clip Plane。
- 将入口和出口变换从“两个 Portal 之间的坐标变换”替换为“同一锚点的缩放、旋转或平移变换”。
- 第一版使用现成 Portal 模型或简单 `prop_dynamic` 作为遮罩，暂不自动识别地图窗户。

#### 展示价值

很高。它能直接表现递归渲染，而且不需要玩家穿越、不需要碰撞桥接，也不依赖复杂地图逻辑。

### 2.4 时间切片走廊

同一条走廊或房间被分割成多个空间切片，每个区域显示不同时间的画面。

#### 核心演出

- 第一区域显示实时世界。
- 第二区域显示约一秒前的世界。
- 第三区域显示冻结帧。
- 玩家或感染者跨过切片边界时，身体可以同时出现在多个时间状态中。

#### 技术层次

- **静态画面版:** 保存 RenderTarget 快照，再通过多个 Stencil 区域重新显示，最快但只有冻结场景。
- **摄像机历史版:** 保存历史视角并重新渲染当前世界，只能产生视角时间差，实体仍是当前状态。
- **实体历史版:** 缓存实体 origin、angles、骨骼或动画状态，重建历史场景，成本和风险都很高。

#### 展示价值

高，但容易被低估技术难度。真正的“过去世界”不仅需要保存画面，还要解决玩家移动后的视差和实体历史状态。

### 2.5 镜像入侵

镜面或反射表面显示一个与现实相似但不完全一致的平行世界，并逐渐出现违反镜像规则的内容。

#### 核心演出

1. 初始阶段是可信的实时镜像。
2. 镜中感染者、队友、灯光或破坏状态开始与现实不同。
3. 玩家停止移动后，镜中的自己仍继续移动或转头。
4. 最后镜中世界可以出现现实中不存在的出口或事件。

#### 可行实现

- 用平面反射矩阵计算镜像相机。
- 用现有 RenderTarget 和 Stencil 将镜像视图限制在镜面模型内。
- 第一版只做世界镜像，不绘制或特殊处理本地玩家模型。
- “入侵”阶段通过过滤模型、替换材质或创建客户端幻象实体实现。

#### 展示价值

很高。它比普通 Portal 更容易被普通观众理解，同时允许逐步加入叙事性异常。

### 2.6 重力剧场

物理世界和玩家移动规则保持不变，但渲染世界围绕玩家旋转，使地面看起来成为墙壁或天花板。

#### 核心演出

1. 玩家触发效果后，地平线开始缓慢倾斜。

2. 世界完成 90 度或 180 度旋转。
3. 玩家仍可正常移动，但视觉上像在墙面或天花板行走。
4. 武器 ViewModel、HUD 和世界可以选择同步旋转或保持稳定。

#### 可行实现

- **相机版 MVP:** 在 `RenderView` 中动画修改 view angles、roll 和 FOV。
- **分离版:** 世界视图旋转，但 HUD 和 ViewModel 使用独立规则。
- **局部重力版:** 只有穿过某个区域或看向某个表面时世界发生旋转。

#### 展示价值

中到高。它非常容易得到动态画面，但仅修改相机时可能被观众理解为“镜头旋转”，技术辨识度不如递归空间或随机门。

## 3. 共同技术底座

六个方向可以共享一套通用框架，而不是各自在 Hook 中堆叠逻辑。

### 3.1 Spatial View

描述一个额外渲染视图：

- 视图 origin 与 angles。
- 相对主视角的变换矩阵。
- RenderTarget。
- Clip Plane。
- 递归深度。
- 可见实体过滤规则。

### 3.2 Spatial Surface

描述额外视图显示在哪里：

- 门框、窗户、镜子或自定义模型。
- Stencil 写入方式。
- 屏幕空间或世界空间遮罩。
- 激活距离与可见性。

### 3.3 Spectacle State Machine

统一管理视觉演出：

- `Idle`
- `Priming`
- `Playing`
- `Holding`
- `Reversing`
- `Cooldown`

现有 Portal 打开/关闭动画状态机已经证明了这种模式比在 `DrawModelExecute` 内隐式修改状态更可靠。

### 3.4 Physical Transition

只有随机门网络等需要真实穿越的插件才启用：

- 门平面穿越检测。
- 位置、速度和视角变换。
- 出口 clearance。
- 碰撞宽限和 Trace bypass。

纯视觉插件不应依赖该层，以降低崩溃和地图兼容风险。

## 4. 实施速度分析

以下排序按“做出一个可录制、能清楚表达概念的 MVP”估算，不代表最终完整版难度。

| 排名 | 方向 | MVP 速度 | 原因 | 主要风险 |
|---:|---|---|---|---|
| 1 | 重力剧场 | 最快 | 已有最终 `CViewSetup` 修改点，只需状态机和角度/FOV 动画 | 容易看起来只是镜头旋转；ViewModel 可能违和 |
| 2 | 无限建筑 | 快 | 几乎完整复用现有递归 Portal 渲染、RenderTarget、Stencil 与 Clip Plane | 渲染状态泄漏、递归性能、遮罩模型选择 |
| 3 | 镜像入侵 | 较快 | 仍是单个额外视图加平面遮罩，反射相机数学明确 | 镜像剔除、手性、玩家模型和透明材质 |
| 4 | 世界折叠 | 中等 | 镜头版很快，但真正折叠需要多个旋转视图和动态分区合成 | 画面接缝、深度关系和运动眩晕 |
| 5 | 时间切片走廊 | 较慢 | 静态快照不难，但可信时间差需要历史画面或实体状态缓存 | 视差错误、显存消耗、实体历史重建 |
| 6 | 随机门网络 | 最慢 | 单门视觉版不难，但完整概念包含门识别、动态连接、穿越、任务流程保护 | 碰撞、导航、地图逻辑、跨地图状态和随机图可达性 |

## 5. 最快方案与最佳首发方案

### 5.1 绝对最快：重力剧场

最小版本只需要：

1. 在 `BaseClient::RenderView::Detour` 中调用独立的视觉状态机。
2. 在数秒内插值修改 `setup.angles` 的 roll、pitch 或 yaw。
3. 加入启用开关和恢复逻辑。
4. 决定 HUD 与 ViewModel 是否保持水平。

它适合用来验证新的通用演出状态机，也适合作为其他插件中的一个视觉阶段，但单独作为项目招牌略显单薄。

### 5.2 推荐首发：无限建筑

如果目标是“尽快做出一眼能看懂的技术展示”，无限建筑比重力剧场更合适：

- 直接展示递归渲染，而不是普通相机动画。
- 不需要处理玩家 teleport、碰撞和速度。
- 可以复用当前最成熟、最独特的 Portal 渲染能力。
- 第一版只需要一个受控遮罩模型，不需要识别所有地图表面。
- 后续可以自然演进到镜像入侵、随机门视觉预览和世界折叠。

建议第一个演示为：在一面墙上放置一个矩形框，框内显示当前房间经过轻微缩放和旋转后的递归版本，每一层增加固定旋转角度和色调偏移，递归深度限制为 3 到 5 层。

## 6. 推荐演进路线

1. **重力剧场原型:** 验证通用视觉状态机、主视角动画和安全恢复。
2. **无限建筑 MVP:** 抽离 Portal 专用命名，形成通用额外视图与表面合成框架。
3. **镜像入侵:** 在相同框架上加入反射变换、实体过滤和异常内容。
4. **世界折叠:** 将多个额外视图同时合成为动态折叠空间。
5. **随机门视觉版:** 将额外视图绑定到地图门框，先不允许穿越。
6. **随机门穿越版:** 接入已有 PortalTransition 和碰撞桥接。
7. **时间切片:** 最后再研究历史 RenderTarget、实体快照和时间视差。

这条路线的关键是先把现有 Portal 渲染能力抽象为可复用的 Spatial View/Surface 系统，但不要在第一个原型阶段进行大规模重构。先通过一个固定表面证明效果，再根据实际重复代码抽取边界。

## 7. 当前共识、分歧与待决事项

### 共识

- 方向以视觉奇观和技术展示为主。
- 可以利用 L4D2 Mod 资源，但第一版优先不依赖额外资源。
- 纯视觉效果应与物理穿越分层，避免每个插件都承担 PortalTraversal 的风险。
- 随机门网络和世界折叠是长期招牌方向。
- 无限建筑适合作为通用空间渲染框架的第一个展示案例。

### 尚未形成结论

- 第一个正式插件是直接制作无限建筑，还是先用重力剧场验证状态机。
- 空间表面第一版使用现成 Portal 模型、地图已有门模型，还是创建一个简单通用框架模型。
- 世界折叠第一版采用纯相机演出还是直接挑战多视图合成。
- 随机门网络是否只支持同一地图，还是最终必须支持跨地图。

### 下一步行动

1. 选择首个实现方向。
2. 为该方向单独编写设计文档，明确视觉脚本、组件边界和 MVP 验收标准。
3. 在设计批准后，再编写实施计划并开始代码修改。
